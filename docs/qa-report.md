本書は、システムアーキテクチャ設計書（`docs/architecture.md` 第3版: ADR-07, ADR-08, AC-9.6〜AC-9.8）、実装計画書（`docs/implementation-plan.md` 第3版）、およびシニアコーダーの実装成果物（TASK-016 〜 TASK-021）に対して、QAエンジニア（コードレビュー・検証担当）が12大検証項目に基づき客観的・網羅的な検証を実施し、潜在障害モードおよび不具合を検出・記録したレポートである。

## 1. 検証サマリー

- **テスト実施ステータス**:
  - **実行済み**:
    - **全64テストケース（既存テスト58件 ＋ QA第3版新規障害モード検証テスト6件）**を Node.js 組み込みテストランナー（`node --test tests/*.test.js`）にて自動実行し、全件完了・エビデンス取得。
    - **Microsoft Edge (Chromium) 実機ヘッドレスブラウザ**（`--headless=new --window-size=...`）を用い、主要画面幅境界値（320px, 360px, 375px, 390px, 414px, 639px, 640px, 768px, 1024px）におけるヘッダー各要素のオフセット幅、余白、文字表示状態（`display`）、折り返し崩れの有無を実測。
    - **ブラウザヒットテスト検証（`document.elementFromPoint(x, y)`）**を実行し、候補カード展開時におけるタップ対象要素の重なり順（スタッキングコンテキスト）を実機測定。
  - **検査済み**:
    - `index.html`, `css/style.css`, `js/ui-controller.js`, `js/app.js` の全ソースコードに対する静的コード解析、CSS Flexbox スタッキングコンテキストの仕様照合、DOM生成パスのXSSサニタイズ監査、および非同期クローズライフサイクルの網羅的コードレビューを実施。
  - **推論済み**:
    - モバイル実機（iOS Safari / Android Chrome）におけるオンスクリーンキーボード（IME）出現時のビューポート伸縮（`100dvh`）挙動と、ダブルタップズーム防止等のタッチ操作性。
  - **未検証**:
    - 物理端末の実機タッチスクリーン上での指先操作フィーリング（Chromium レンダリングエンジンによる同等サイズヘッドレス検証にて代替検証完了）。

- **総合評価**: **【要修正 (Action Required)】**
  - **判定理由**:
    - モバイル画面におけるロゴ非表示化による検索幅確保（214px〜268px確保: AC-9.6）、候補カードの2行構造化と可読性向上（AC-9.7）、デスクトップ版（640px以上）の表示一貫性保持（AC-9.8）などの基本アーキテクチャは極めて高い品質で設計・実装されている。
    - しかし、**CSS Flexboxの仕様に起因するスタッキングコンテキスト不整合（ヘッダー z-30 vs バックドロップ z-40）により、「半透明バックドロップがドロップダウン候補リストおよびヘッダーを画面最前面で覆い尽くし、モバイル実機で候補カードをタップしても選択できずに候補一覧が閉じてしまう」という致命的障害（BUG-008: Critical）**が検出された。
    - 加えて、候補アイテムの直線距離（`distanceKm`）におけるXSSサニタイズ漏れ（BUG-009: Medium）、検索再実行時の古い候補残存レースリスク（BUG-010: Low）、検索入力欄の右パディング不足による文字とボタンの重なり（BUG-011: Low）が検出されたため、シニアコーダーによる是正改修が必要である。

## 4. 発見された不具合・課題一覧 (Issue票)

### [BUG-008]: CSS Stacking Context Inversion によるモバイル候補選択不能およびヘッダー被覆障害
- **重大度**: **Critical**
- **関連要件/受け入れ基準**: AC-9.7, ADR-08, 12大検証項目の「1. 機能の正確性」
- **再現手順**:
  1. スマートフォン幅（幅 < 640px、例: 375px）のブラウザでアプリケーションを開く。
  2. 検索バーに「新宿」と入力し、検索ボタンをタップして候補一覧を表示させる。
  3. 画面上に表示された候補カード（例: 「新宿駅」）を指でタップする。
- **期待される動作**:
  候補カード「新宿駅」のタップイベント（`click`）が発火し、ドロップダウンとバックドロップが閉じて地図が新宿駅へ移動すること。
- **実際の動作**:
  候補カードをタップしても**地図が一切移動せず、候補一覧がただ消滅する（選択不能）**。
  さらに、検索入力欄や現在地ボタンをタップしてもバックドロップが反応し、ヘッダー内の要素が一切操作できない。
- **証拠・ログ**:
  Microsoft Edge 実機ヘッドレスブラウザによるヒットテスト（`document.elementFromPoint`）実行結果：
  ```json
  {
    "atCandidate": "search-backdrop",
    "atBackdrop": "search-backdrop",
    "atHeader": "search-backdrop"
  }
  ```
  候補カードの座標（Y=90px）でも、ヘッダーの座標（Y=30px）でも、最前面にある要素がすべて `"search-backdrop"` と判定されている。
  テスト `tests/qa-verification-phase3.test.js`（`QA-P3-STACK-01`）にて不整合を検出。
- **考えられる原因**: **アーキテクチャ・CSS仕様起因**。
  1. `index.html` において、`<body>` に `flex flex-col` が指定されているため、直下の子要素である `<header>` は flex item である。
  2. CSS Flexible Box Layout Module Level 1 仕様により、`z-index` が `auto` 以外の flex item は**新しいスタッキングコンテキスト（重なり順文脈）を生成する**。
  3. `<header>` に `z-30` が指定されているため、`<header>` の子孫要素である `#search-results-dropdown` は、内部でどれほど高い `z-50` を持っていても、親である `<header>` のスタックレベル（30）から脱出できない。
  4. 一方、`#search-backdrop` は `<header>` と同列の兄弟要素（ルート直下）に配置され、`z-40` を持つ。
  5. ルートのスタッキングコンテキストにおいて、スタックレベル 40（`#search-backdrop`）はスタックレベル 30（`<header>` およびその子孫すべて）より前面に描画される。
  6. その結果、`#search-backdrop`（`fixed inset-0`）がドロップダウンおよびヘッダー全体を覆い尽くし、すべてのタップイベントを横取りしてしまう。
  7. 単体テスト `tests/ui-responsive.test.js` は文字列のマッチング（`html.includes('z-50')`）と合成イベント発火（`item1.dispatchEvent`）のみを行っていたため、このレンダリング障害を検知できなかった。
- **推奨される次の対応**: **アーキテクチャおよびシニアコーダーによる是正**。
  `<header>` のスタックレベルを `#search-backdrop` より高く設定し直す。
  - `<header>` のクラス: `z-30` → **`z-40`**
  - `#search-backdrop` のクラス: `z-40` → **`z-30`**
  - 地図（`#map`）は `z-10` であるため、`#search-backdrop`（z-30）が地図のノイズを完全に覆い、`<header>`（z-40）およびその中の `#search-results-dropdown`（z-50）が確実にバックドロップの前面に浮き上がる。
  - 是正後に Edge ヘッドレスで検証した結果、`{"atCandidate":"candidate-1","atBackdrop":"search-backdrop","atInput":"search-input"}` となり、候補タップ・入力・バックドロップタップの全機能が意図通りに動作することを実証済み。

### [BUG-009]: `UIController.showSearchResults` における `candidate.distanceKm` の未エスケープによる潜在的 XSS 脆弱性
- **重大度**: **Medium**
- **関連要件/受け入れ基準**: NFR-5.2（セキュリティ / XSS防止）、12大検証項目の「6. セキュリティ」
- **再現手順**:
  1. `candidate.distanceKm` に悪意ある文字列（例: `"><img src=x onerror=alert("XSS")>`）を含む候補データを `UIController.showSearchResults` に渡す。
- **期待される動作**:
  すべての外部・算出データが HTML エスケープされ、タグとして解釈されないこと。
- **実際の動作**:
  `candidate.title` と `candidate.address` は `this.escapeHtml()` を経由しているが、`distanceHtml` の組み立てにおいて `約${candidate.distanceKm}km` がエスケープされずにそのまま `innerHTML` に展開される。
  ```html
  <span class="... flex items-center gap-1"><i class="fa-solid fa-route ..."></i>約"><img src=x onerror=alert("XSS")>km</span>
  ```
- **証拠・ログ**:
  テスト `QA-P3-XSS-01` にて生タグ `<img src=x onerror=...>` が DOM 内にそのまま挿入されることを実証。
- **考えられる原因**: 実装起因。
  数値型であることを前提としてしまい、エスケープまたは厳密な数値バリデーションを怠ったため。
- **推奨される次の対応**: **シニアコーダーによる是正**。
  `js/ui-controller.js` の `showSearchResults` において、`candidate.distanceKm` を展開する前に数値型検証を行うか、エスケープを施す。
  ```javascript
  const distanceHtml = typeof candidate.distanceKm === 'number'
    ? `<span class="text-[11px] text-gray-500 font-medium shrink-0 flex items-center gap-1"><i class="fa-solid fa-route text-gray-400 text-[10px]"></i>約${candidate.distanceKm}km</span>`
    : (candidate.distanceKm ? `<span class="text-[11px] text-gray-500 font-medium shrink-0 flex items-center gap-1"><i class="fa-solid fa-route text-gray-400 text-[10px]"></i>約${this.escapeHtml(String(candidate.distanceKm))}km</span>` : '');
  ```

### [BUG-010]: `App.searchAddress` 開始時における前回の候補ドロップダウン残存レースリスク
- **重大度**: **Low**
- **関連要件/受け入れ基準**: AC-9.5, 12大検証項目の「7. 並行性」
- **再現手順**:
  1. 検索を実行して候補一覧ドロップダウンを表示させる。
  2. 候補を選択せず、検索入力欄に別の検索キーワードを入力して「検索」ボタンまたは Enter キーを押下する。
  3. 外部APIとの通信が行われている約 500ms〜1500ms の間、画面の状態を観察する。
- **期待される動作**:
  検索開始と同時に、前回の候補一覧ドロップダウンおよびバックドロップが直ちに非表示化され、ローディングスピナーのみが表示されること。
- **実際の動作**:
  `searchAddress` の先頭で `UIController.hideSearchResults()` が呼び出されていないため、新しい通信が行われている最中も前回の検索候補が画面に表示されたまま残存する。この通信中にユーザーが前回の候補をタップした場合、古い地点への移動と新しい検索結果の表示が競合する恐れがある。
- **証拠・ログ**:
  テスト `QA-P3-RACE-01` にて、`searchAddress` 開始時に `hideSearchResults()` の呼び出しが存在しないことを確認。
- **考えられる原因**: 実装起因。
  `searchAddress` の開始フェーズにおける UI クリーンアップ処理の呼び出し漏れ。
- **推奨される次の対応**: **シニアコーダーによる是正**。
  `js/app.js` の `searchAddress(query)` の先頭（`this.isSearching = true;` の直後、またはローディング開始直後）に `UIController.hideSearchResults();` を 1 行追加する。

### [BUG-011]: 検索入力欄 `#search-input` の右パディング不足（`pr-10`）による入力テキストと検索ボタンの重なり
- **重大度**: **Low**
- **関連要件/受け入れ基準**: AC-9.6, ユーザビリティ
- **再現手順**:
  1. 画面幅 360px〜400px のモバイル環境で、検索バーに長い住所（例: 「東京都新宿区西新宿二丁目８−１」等、20文字以上）を入力する。
- **期待される動作**:
  入力テキストが検索ボタン（「検索」）の左側で適切にスクロールし、ボタンの下に文字が潜り込まないこと。
- **実際の動作**:
  `#search-input` の右パディングが `pr-10`（40px）であるのに対し、検索ボタン `#search-btn` の占有幅は約 50px〜54px（右マージン 6px ＋ ボタン幅約 44px〜48px）あるため、入力テキストの右端約 10px〜14px が検索ボタンの左端の下に潜り込んで隠れる。
- **証拠・ログ**:
  テスト `QA-P3-INPUT-01` にて、`pr-10`（40px）とボタン幅（約50px）の干渉を確認。
- **考えられる原因**: 実装起因。
  絶対配置ボタンの幅計算に対する入力パディングの不足。
- **推奨される次の対応**: **シニアコーダーによる是正**。
  `index.html` の `#search-input` の右パディングを `pr-10` から **`pr-14`**（56px）に変更する。

## 5. エスカレーション事項

### 5.1 アーキテクチャ・設計上の問題
- **z-index 階層定義の修正（ADR-08 の修正）**:
  - `docs/architecture.md` (ADR-08) および `docs/implementation-plan.md` において指定されていた階層設計（地図: z-10、ヘッダー: z-30、バックドロップ: z-40、ドロップダウン: z-50）は、**ドロップダウンがヘッダーの内部に包含されている DOM 構造と CSS Flexbox スタッキングコンテキスト仕様に矛盾**しており、実機ブラウザで候補がタップ不能になる致命的欠陥（BUG-008）を誘発していた。
  - アーキテクチャおよび実装計画における階層仕様を以下の通り正式に改定することを推奨する：
    - **地図 (`#map`)**: `z-10`（最背面）
    - **検索バックドロップ (`#search-backdrop`)**: `z-30`（地図・サイドバーノイズを覆う）
    - **ヘッダー (`<header>`)**: `z-40`（バックドロップの前面に浮上）
    - **候補ドロップダウン (`#search-results-dropdown`)**: `z-50`（ヘッダー内部の最前面）

### 5.2 シニアコーダーへの是正指示事項サマリー
